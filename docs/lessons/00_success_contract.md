# Lesson 00 — Understand the success contract

Status: implemented offline demonstration. All answers, facts, and reviews are synthetic/demo-authored. No live agent, SQL query, or LLM judge runs in this lesson.

[Lesson index](README.md) · [Executable notebook](../../notebooks/00_success_contract.ipynb) · [Evaluator source](../../src/finance_evals/contracts.py)

## 1. The business question

A finance analyst asks:

> Why did Marketplace revenue decline last month?

We fix today to November 18, 2026. Last month is October; its comparison month is September. The supplied facts are September net revenue of $10 million and October net revenue of $9 million: a decrease of $1 million, or 10%.

Available evidence contains monthly totals only. It does not establish the business cause. Under this case's success contract, an acceptable answer reports the verified change and explicitly acknowledges that limitation. This is acceptable handling of limited evidence, not a completed root-cause investigation.

## 2. What the lesson accomplishes

Separate three things: the candidate answer, the expected facts, and the assessment of its explanation. Combine their checks without allowing correct numbers to conceal an unsupported claim.

Inputs: three authored candidate answers, one reference case, and three authored narrative reviews.
Output: per-check verdicts and an overall verdict for each answer.
Next lesson: establish expected facts from synthetic source records and independently verified database calculations.

## 3. File responsibilities in an enterprise setting

| File | Meaning now | Enterprise equivalent | What it is not |
|---|---|---|---|
| [lesson00_answers.json](../../evals/cases/lesson00_answers.json) | Three possible agent outputs, deliberately written to illustrate different failures | Captured output of a particular agent trial, tied to case/run/model versions | Not the golden answer set; some candidates are intentionally wrong |
| [revenue_case.json](../../evals/reference/revenue_case.json) | One case containing expected fields, metadata, and an evidence limitation | Evaluator-owned expectations supported by an approved definition, independent reference query, and fixed data snapshot | Not a raw SQL record and not generated by the agent under evaluation |
| [lesson00_reviews.json](../../evals/reviews/lesson00_reviews.json) | Supplied judgments about each exact narrative | Human review or a calibrated LLM judge's assessment of answer claims against evidence | Not the reference facts and not proof an LLM judge has run |
| [contracts.py](../../src/finance_evals/contracts.py) | Field comparisons, review matching, and verdict aggregation | A small part of a broader evaluation pipeline | Not yet a general grounding evaluator or trajectory checker |

The current review verdict is the string `pass` or `fail`, not the Boolean `true` or `false`. Evaluation may also return `unverifiable` when no valid review is available.

A golden dataset would contain multiple cases with questions, expected facts and behavior, reference evidence, and provenance. Here, `revenue_case.json` is one demo reference case. The natural-language question currently appears in the notebook, rather than as a field in that JSON. Future cases should carry the question explicitly.

## 4. The schemas

### Candidate answer

```json
{
  "id": "unsupported_churn",
  "narrative": "Marketplace net revenue declined from $10 million in September to $9 million in October, a decrease of $1 million (10%), caused by customer churn.",
  "scope": "Marketplace",
  "metric": "net_revenue",
  "prior_period": "2026-09",
  "current_period": "2026-10",
  "prior_cents": 1000000000,
  "current_cents": 900000000,
  "change_cents": -100000000,
  "change_pct": "-10.00"
}
```

The narrative is user-facing text. The structured fields make exact checks possible. Both describe the same response and should agree, although this first evaluator does not implement a general prose-versus-fields consistency check.

### Reference case

```json
{
  "case_id": "revenue_001",
  "version": "1",
  "fixed_today": "2026-11-18",
  "review_status": "demo_authored",
  "reference": {
    "scope": "Marketplace",
    "metric": "net_revenue",
    "prior_period": "2026-09",
    "current_period": "2026-10",
    "prior_cents": 1000000000,
    "current_cents": 900000000,
    "change_cents": -100000000,
    "change_pct": "-10.00"
  },
  "evidence_limit": "Monthly totals establish the change, but do not establish its business cause."
}
```

Amounts are integer cents: 1,000,000,000 cents equals $10 million. The percentage is currently a formatted string.

**Correction about evidence_limit:** this is an evaluator-authored description of the available evidence. It is not a Boolean flag and is not created by the agent. In a real system, the agent should disclose its evidence limitations in its response; the evaluator independently checks whether that disclosure and the claims are appropriate.

The agent's SQL query is also not automatically the reference query. A wrong query can return a convincing result. The independent reference must use agreed metric definitions and the same data version, with its own verification.

### Narrative review

```json
{
  "answer_id": "unsupported_churn",
  "narrative": "Marketplace net revenue declined from $10 million in September to $9 million in October, a decrease of $1 million (10%), caused by customer churn.",
  "verdict": "fail",
  "reason": "Monthly totals do not establish churn as the cause.",
  "reviewer": "demo_author",
  "review_status": "demo_authored"
}
```

The review says: “I assessed this explanation and found its churn attribution unsupported.” Repeating the narrative binds the review to the exact text assessed; an edited narrative invalidates that match. This is a simple stale-review check, not authentication of the reviewer.

## 5. What evaluate(answer, reference, review) does

The actual function signature is:

```python
def evaluate(answer, reference, narrative_review=None):
```

A variable named `review` can be supplied positionally. If using a keyword, use `narrative_review=review`.

| Argument | Source | Purpose |
|---|---|---|
| answer | One candidate in answers | Actual output being checked |
| reference | case["reference"] | Expected factual fields |
| review | Matching item in reviews | Existing assessment of the narrative |

### A. Numerical comparison

The function compares `prior_cents`, `current_cents`, `change_cents`, and `change_pct`. Every value and its Python type must match the reference.

It does not calculate the reference or independently recompute the percentage here. The notebook uses `percentage_change()` separately to demonstrate arithmetic. Missing numerical fields fail their comparisons.

Current limitation: exact string equality makes `"-10.0"` differ from `"-10.00"`. Later graders should normalize numeric values and use declared tolerances.

### B. Scope and period comparison

Compare `scope`, `metric`, `prior_period`, and `current_period`. Correct numbers for the wrong month must fail this check.

### C. Review matching

A usable review must be a dictionary with the same answer ID and exact narrative, a pass/fail verdict, and a nonempty reason.

`review_ok` means the review is usable, not that the answer passed. A usable review can contain a fail verdict. If usable, its verdict becomes `claims_supported`; otherwise that check is `unverifiable`.

The function does not independently understand the narrative, verify the reason, authenticate the reviewer, or enforce SME approval. It also does not consume the case's `evidence_limit` or `fixed_today` fields: only the nested reference is passed in. The supplied review already reflects the evidence limitation.

### D. Overall verdict

```python
# Readable equivalent of the aggregation:
if "fail" in checks.values():
    overall = "fail"
elif all(value == "pass" for value in checks.values()):
    overall = "pass"
else:
    overall = "unverifiable"
```

An explicit failure takes precedence. When no check fails but a required review is unavailable, the answer remains unverifiable.

## 7. Follow the churn example through the whole evaluation

The user asks:

> Why did Marketplace revenue decline last month?

The candidate answer says:

> Revenue fell from $10 million to $9 million, a decrease of 10%, caused by customer churn.

The evaluator receives:

```python
answer = answers[1]         # Candidate containing the churn claim
reference = case["reference"]
review = reviews[1]        # Supplied review rejecting that claim

result = evaluate(answer, reference, review)
```

The result is:

```json
{
  "answer_id": "unsupported_churn",
  "checks": {
    "numbers_correct": "pass",
    "scope_and_period_correct": "pass",
    "claims_supported": "fail"
  },
  "overall": "fail",
  "review_reason": "Monthly totals do not establish churn as the cause.",
  "mode": "offline_authored_examples"
}
```

The final result is a failure because **the user asked for an explanation, and the answer presented an unsupported cause as fact**. In this implementation, the supplied review identifies the unsupported cause; the evaluator carries that judgment into the overall result.

| Candidate | Numbers | Scope and periods | Narrative review | Overall |
|---|---|---|---|---|
| limited_evidence | Pass | Pass | Pass | **Pass** |
| unsupported_churn | Pass | Pass | Fail | **Fail** |
| wrong_period | Pass | Fail | Pass | **Fail** |
| Acceptable candidate without a review | Pass | Pass | Unverifiable | **Unverifiable** |

The review for `wrong_period` passes because it assesses the narrative, which still states the expected months. The separate structured-period check fails the answer overall: its `current_period` is `2026-08`. This narrow review does not approve the whole answer.

The fourth row is an additional evaluation condition, not a fourth object in the answers file:

```python
assert evaluate(answers[0], reference)["overall"] == "unverifiable"
```

## 8. How this becomes an enterprise workflow

| Stage | Future enterprise-style behavior |
|---|---|
| Prepare case | Finance/data owners establish the question, definition, access scope, snapshot, and success criteria |
| Establish expected truth | Execute and verify an independent reference query or calculation |
| Run application | Azure OpenAI agent uses governed tools and produces structured facts, narrative, and evidence pointers |
| Capture evidence | Persist trace, actual queries, tool results, scope, periods, and versions |
| Grade exact requirements | Compare numerical results, business semantics, and required controls |
| Review meaning | A human or calibrated judge assesses claims against actual evidence |
| Aggregate | Produce an overall verdict with per-check findings and references |
| Decide | Inspect failures, compare versions, and apply release criteria |

These are future extensions. Lesson 00 implements the last comparison/aggregation concepts using authored inputs. It does not establish a real model's success rate.
